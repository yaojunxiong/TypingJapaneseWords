# 孤立录音处理记录

## 问题描述
YOYO 账号（user_id: `942e0c94-2693-4f5a-888d-f4c7a390533f`）的 2 条录音在 DB 中标记为 `uploaded`，但对应的 Storage object 已不存在（`createSignedUrl` 返回 `"Object not found"`）。

### 孤立录音详情
| ID | 课 | 句 | take_no | storage_path |
|---|---|---|---|---|
| `9d0fc910-575f-4fa9-a401-183c33bbc31a` | 1 | 1 | 4 | `942e0c94/lesson-1/line-1/mquexi5v-h3q7bojx.webm` |
| `aaef1ed1-5dfc-4b06-b5a2-586f66ff7bb4` | 1 | 1 | 3 | `942e0c94/lesson-1/line-1/mquewuiw-fargcukt.webm` |

## 根因
旧 upload 逻辑（service-role 改造前）使用普通 Supabase 客户端上传到 Storage：
1. Storage 上传成功（文件写入）
2. DB insert 失败（如 take_no 唯一约束冲突）
3. DB insert 失败后的 `storage.remove([storagePath])` 清理删除了 Storage 文件
4. 但客户端重试时，新录音取得了新 take_no，DB insert 成功
5. 最终 DB 有记录，但 Storage 文件已被前次失败清理删除

## 修复方式
- 通过 admin client 调用 `createSignedUrl` 检测 Storage object 是否存在
- 对孤立的 DB 记录设置 `deleted_at = now()`（软删除，不硬删除）
- 前端列表 API 过滤 `.is('deleted_at', null)`，孤立记录不再显示

## 长期预防
新 upload API（commit `64b8b31` 起）已解决：
1. **Service-role 上传**：`createAdminClient()` 使用 `SUPABASE_SERVICE_ROLE_KEY` 上传，不受 Storage RLS 限制
2. **UUID 唯一路径**：storage path 使用 `{userId}/lesson-{x}/line-{y}/{timestamp}-{random}.webm`，不依赖 take_no
3. **DB 失败清理也用 service-role**：用 `storageClient.storage.remove([storagePath])` 在 DB insert 失败时清理
4. **take_no 查询无 deleted_at 过滤**：commit `8090f23` 修复

## 如何检测孤立录音
```sql
-- 需要通过 admin client 逐一调用 createSignedUrl 检查
-- 如果返回 "Object not found"，则该记录为孤立
const { data: sd, error: sdErr } = await adminClient.storage
  .from('recordings')
  .createSignedUrl(t.storage_path, 30)
const isOrphan = sdErr?.message === 'Object not found'
```
